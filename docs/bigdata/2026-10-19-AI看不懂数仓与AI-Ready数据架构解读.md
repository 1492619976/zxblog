# AI 看不懂数仓与 AI-Ready 数据架构（解读速记）

> 一句话：数仓完成了**技术整合**，没完成**业务语义的标准化表达**——DataAgent 时代在现有数仓上补四层能力（供得上/信得过/用得动/给得安全），不推翻重建。
> 文章性质：帆软系软文（推 FineDataLink 5.0），产品段落过滤掉读，框架部分独立成立。

## 为什么 AI 看不懂（诊断）

- 传统数仓的默认前提 = 使用者懂业务：字段含义/指标口径/粒度规则散落在 SQL 脚本、指标文档和开发经验里，没有沉淀进数据模型
- 典型症状：混淆订单金额/确认收入/实际回款；忽略去重规则和有效客户定义；SQL 能跑 ≠ 结果对
- 宽表思维三不够：①字段多 ≠ AI 懂（"会关联"≠"会正确关联"——订单明细一行一商品 × 回款一行一笔收款，直接关联求和必重复计算）②预设计宽表覆盖不了动态跨主题问题③"有效订单"这类业务规则困在 SQL 任务里，机器读不到

## AI-Ready 数据架构四要素（怎么做）

1. **供得上**（集成层）：关键业务链路优先，不盲目扩数仓规模；批量/CDC/API/消息队列按数据特性分流；信创库（达梦/金仓/OceanBase/GaussDB）日志解析级 CDC
2. **信得过**（质量+血缘）：质量三层 = 源头合规 / 加工一致 / 消费达标；**任务成功 ≠ 数据正确**（订单同步正常但源状态字段变化→错算有效销售额）；质量规则要关联业务指标（主键唯一/跨表关联完整性/金额勾稽/更新时效/异常波动）；血缘说明"从哪来"但替代不了口径定义，两者结合
3. **用得动**（语义层，核心）：统一指标定义八要素 = 名称/计算公式/统计粒度/时间口径/组织范围/过滤条件/数据来源/负责人；**多口径不合并**——财务口径（不含税·下单日期·集团）与销售口径（含税·签约日期·本公司）分版本标识适用范围，Agent 按提问场景选；按业务主题组织数据资产限定检索范围（先主题后全库）；业务规则变成可执行语义资产（指标定义关联 SQL 表达式、连接键+基数约束、口径变更留版本）
4. **给得安全**（服务层）：不给 Agent 开生产库/大范围数仓账号；数据能力封装 API + MCP 受控输出；权限校验/鉴权/限流/审计/敏感操作人工审批

## 老数仓四步改造（已有几百张表）

① 盘点数据资产：选经营/财务分析等定义明确领域先行，认证指标+模型 = 第一批 AI 可用资产（评估标准不是开放多少表，而是业务含义清/更新机制稳/使用权限明）
② 补质量与血缘：核心资产向上追溯来源与加工链路；未过质量检查 → 告警/标记不可用/阻断发布，不一律放给 AI 消费
③ 建语义层：高频业务问题 → 指标/维度/数据服务映射；三个测试比"SQL 能否执行"更有价值 = 换表达方式仍选同口径 / 多表关联不重复计算 / 时间范围变化正确处理统计周期
④ API+MCP 受控消费：权限审计+结果验证（用对指标/访问授权数据/满足时效/可追溯）；建指标变更、模型调整、接口版本的影响评估机制，防"底层已改、Agent 还用旧规则"

## 7 个衡量指标（AI-Ready 数据架构改造效果）

语义覆盖率（核心指标有统一定义的比例）/ 口径一致率 / 数据时效性（结果对应的数据时间点与更新频率）/ 质量达标率 / 服务可用性 / 权限覆盖率 / AI 调用准确率（与既定口径符合程度）
