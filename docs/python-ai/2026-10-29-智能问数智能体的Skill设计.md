# 🧩 智能问数智能体的 Skill 设计

> 来源：公众号「小强匠」（作者小强）《智能问数智能体的Skill设计》2026-09-27，"智能体开发实践"系列第 3 篇 · 桌面扫描版 PDF（7页）已 OCR 全文转录后解读

## ❓ 问题

问数类（ChatBI/NL2SQL）Agent 的 Skill 和主流文本型 Skill 有什么本质不同？思维链（CoT）架构为什么在复杂问数场景力不从心，怎么改造成 Skill 架构？

## 💡 答案/要点

**一句话**：问数场景对"准、稳定复现、快"的要求，决定了问数 Skill 不能靠纯文本提示词，而要走**声明（SKILL.md 等，人维护）与代码（engine 等框架，自动编译执行）分离**的架构——本质是把软件工程经典设计模式在 Skill 理念下再适配一遍。

### 01 思维链架构：能跑 MVP，但复杂场景会"臃肿成散文"

- 智能问数典型知识分层：**元数据 → 指标 → 思维链（CoT）→ 分析报告**（思维链是产品核心载体，串联指标与元数据；报告=思维链半成品+预置模板组装）
- 还原一份经营分析报告的生产过程 = 五步：①报告有哪些分析内容与步骤逻辑 ②每步的计算指标/原始数据/公式/数据出处 ③拼装形式（文字/表格/图表）与格式要求 ④深层分析推理方向 ⑤章节/数据/样式模板要求 → 归纳为六步：**学习、溯源、统计、推理、组装、校验**
- 人只做两件事：告诉智能体**工作从哪来（数据来源）、到哪去（报告示例）**，其余自主学习形成思维链（资料投喂→提取思维链/指标/模板→MCP 映射物理数据→梳理步骤→自我验证）
- 优势：面向业务容易提取、业务/设计人员易理解、实现快——MVP 阶段非常友好
- **不足**（关键转折）：思维链是"一纸禅"式设计，复杂业务场景下关键要素（指标/数据/维度）太多 → 出问题难追溯、迭代难维护、结果难校验——"简洁的作业指导手册变成四处发散的散文"。思维链不是不好，是**复杂且高频**的场景力不从心

### 02 Skill 架构：Skill 是设计模式，不是具体技术

- Skill 的根本价值：**解决了"如何让模糊的 LLM 与具体物理世界准确交互"的机制问题**
- Anthropic Skill = 给智能体的标准作业程序（SOP）：指令+脚本+资源打成文件夹，碰到相关任务主动翻阅；核心机制 = **渐进式披露**（先只看目录→对上再读正文→做到那步才翻脚本和附录，避免整本手册塞进上下文）
- 通用目录形态：`SKILL.md / references / scripts / assets / checks`——"一份写给智能体看的说明书，不是给人看的 PPT"；靠谱的 Skill 是一整套对得上的东西：主说明书管触发和步骤、参考管口径、脚本管执行、检查管验收

### 03 问数类 Skill 的四点不同（本文核心增量）

问数核心场景 3 类：**要数 / 基于数的二次计算 / 基于数和业务逻辑的分析推理**；统一围绕 3 条核心技术要求：**要准、要稳定复现、要尽可能快**（普通语言任务少 1-2 个词无伤大雅，问数少 1 个数、错 1 个小数位是致命的）。由此四点设计不同：

1. **不能使用纯文本操作指令**——写得再多再细都不行，文本（提示词）在大模型执行过程中非常不可信
2. **要配套完善的 MCP 等工具与数据底座交互**——不是每次由智能体临时、自主思考选择
3. **要配一整套硬编码的数据及逻辑验证脚本**——哪怕只作为最后佐证，代码规模甚至跟正常业务代码量差不多
4. **要配置编译和执行引擎（engine）+ 运行时框架**——不指望 LLM 积极执行

> 80/20 法则：花 80% 精力解决大模型无法解决的那 20% 问题（幻觉、追溯、检查）；且这 80% 是**一次性投入持续发挥作用**，像打地基。

### 04 改造思路：思维链 → 声明 + 代码分离

不是全新设计，是把思维链当对象做提炼改造：把思维链中的业务要素全部提炼出来，按 Skill 模式放到对应位置重新组装。

**声明部分（人工维护，SKILL.md 为唯一维护源）——五件套：**

| 文件 | 职责 |
|---|---|
| `SKILL.md` | 内容：职责边界、入参契约、取哪些量、怎么归约 |
| `rules/` | 阈值：场景参数、门限；等级（优良中差分档由框架内置工具判定） |
| `checks/` | 检验：**四级检查 C1 看原料 / C2 看计算自洽 / C3 看叙述逻辑及数据溯源 / C4 看输出表列和图表** |
| `templates/` | 模板：句式、报告大纲、公文样式，不能写死在组装代码里 |
| `_build/` | 编译产物（manifest.json 等，自动生成勿手改） |

**代码部分（框架层）：** engine（按声明顺序执行）+ registry（启动校验）+ runner（场景编排）+ compiler（根据 Skill 声明自动编译必要代码）+ C1-C4 分层检查。Scenario（场景）编排**只调度节点**；运行结果（各节点真实数据）作为下次优化输入。

### 金句

- 思维链是二维的（从前到后、从主到分）；**Skill 是三维的（树形展开、按需调用）**
- Skill 不是新东西，只是把经典设计模式在大模型架构下再次调整适配
- 最像 IoT 架构：IoT 把物理世界表征转化为数据信息，Skill 把 LLM 的不确定性思考逐步转化成明确可执行的逻辑，驱动具体业务系统
