# Data Agent 深度调研报告（2026版）解读

## 报告是什么

公众号文章导出 PDF，参考《AI Agent 深度调研报告（2026版）》框架写的企业级 Data Agent 赛道综述。报告自己声明了可信度分层：标"据厂商官方文档/据一线实践"的是一手事实，市场规模/渗透率是预测性数据。五段结构：定义边界 → 技术架构 → 市场格局 → 深度案例 → 落地指南。

## 核心论点（骨架）

1. **定义**：Data Agent = LLM 大脑 + 数仓手脚的自主智能体，覆盖三层——消费侧（问数/归因/报告）、平台侧（元数据/血缘/质量）、研发侧（ETL 生成/管道编排/异常诊断）。与 ChatBI 分水岭：ChatBI 止步于"查"，Data Agent 强在"做"（写回/建管道/改配置）；ChatBI 是人找数，Data Agent 是数找人。
2. **六层参考架构**（报告以开源项目 DSH 为参考实现）：L1 智能编排（LLM 规划，**全栈唯一 LLM 层**）/ L2 工具接口（MCP 事实标准）/ L3 确定性引擎（零 LLM：校验/翻译/执行/渲染）/ L4 本体语义层（指标/实体/关系）/ L5 记忆层 / L6 观测层（trace/评测/成本）。原则：**LLM 只做规划，确定性交给工程**。
3. **四个可复刻工程模式**：
   - NL → MQL → SQL 两段式：理解侧 LLM 只生成纯业务语义的 MQL（出现物理表名/字段名=格式错误直接拒绝）；执行侧零 LLM 规则翻译，指标按归属对象分组（同对象合并单表、跨对象 CTE 对齐）
   - OAG 对象-属性图检索：表-列-指标-业务词四类节点，LLM 图上走两跳拿到带口径和 JOIN 关系的上下文
   - 零 LLM 确定性引擎：只读会话+超时控制+行数上限+EXPLAIN 预检，性能可预算、结果可复现
   - 人在回路：歧义澄清、执行前确认、反馈回收做成产品级交互
4. **语义层是最热战场也是最大瓶颈**：两种路径——语义层即模型（dbt SL/Cube，指标定义收口）vs 语义层即词典（Berdite/dbt-mcp，开发者局部理解做成标注）。判断：没有语义层的 NL2SQL 是空中楼阁；**瓶颈不是模型，是语义层建设滞后**。
5. **单 Agent 优先**（2026 共识）：一个 Agent+强工具箱，Anthropic"够用就好"；多 Agent（编排者+专业 worker）调试难/成本翻倍/延迟叠加，跑不通再拆。
6. **记忆三层**：工作记忆（上下文窗口+scratchpad）/情景记忆（向量库会话摘要）/语义记忆（知识库+语义层 RAG）。**口径文档做 RAG 是企业落地最普遍路径**。
7. **演进路径**：prompt → context → harness → loop（2026 里程碑=自主循环 感知→规划→行动→观察）。

## 市场格局速览

- 数据库厂商：Databricks 系统设计 Agent（GA，查目录→诊断→改参数→写回+人在回路）、Snowflake Cortex Analyst（宣称 90%+，核心是 YAML 语义模型）、BigQuery Gemini
- BI 厂商：Tableau Pulse（洞察摘要+异常解释）、Power BI Copilot、ThoughtSpot Analytics Agents
- 国内：阿里瓴羊 Quick BI 问数、腾讯 ChatBI；字节内部平台、快手 DataAgent（**先治理后问数**：治理容错率高，问数错一个数就失去信任）、蚂蚁图+Agent
- 开源：Vanna.ai（DDL+历史 QA 对+文档三样做 RAG；**问答对是最值钱资产，冷启动人工写 50 个高质量 QA 比调 prompt 有效**）、WrenAI、DB-GPT、DSH
- 定价观察：Databricks 按 vPU 秒、Snowflake 按 query credit；**厂商卖的是引擎，口径（语义模型）永远要自己建**

## 落地指南

选型三问：需求在消费侧还是研发侧？有没有语义层（没有先补，别急着上 Agent）？开箱即用产品的语义模型也要自己建。
四阶段：0 治理（指标盘点/字典 v1）→ 1 试点（NL2SQL 选 1-2 主题域+评测集）→ 2 扩展（语义层 v2+治理 Agent）→ 3 深水区（写操作人工审批+审计回滚）。

## 六大功能×痛点（2026-10-20 用户拍板：后续建设中分别做的项目）

| # | 项目 | 解决的用户痛点 | 现有起点 |
|---|------|--------------|---------|
| 1 | 问数 NL2SQL（Cortex Analyst 路线，宣称 90%+） | 取数要排期、业务不会 SQL，分析师 80% 时间在写重复 SQL | data-toolbox P4b ChatBI 最小闭环（mock 三路径全绿，真 Key 待配）；掌柜问数 RAG 骨架 |
| 2 | 洞察推送/异常解释（Tableau Pulse 路线） | 仪表盘没人看——数不会找人 | 新起；可结合指标卡片库做主动异常解释 |
| 3 | 报告自动生成 | 周报月报手工拼数 | 新起；周报生成工作流是雏形 |
| 4 | 治理 Agent（快手路线：元数据/血缘/质量检核） | 数据字典没人维护、血缘靠人脑记 | data-toolbox 治理模块（盘点/资产目录/词根/血缘）Agent 化升级 |
| 5 | ETL 生成/管道编排/异常诊断 | 研发侧重复劳动、夜批排查靠老中医把脉 | 夜批诊断=pdi 日志分析方法论；配套已有 .ktr/.kjb 生成器 |
| 6 | 系统运维 Agent（Databricks 路线：查目录→诊断→改参数→写回） | Spark UI 都查不出的问题 | OB 性能体检报告经验可迁移 |

建设节奏可参考报告落地四阶段（治理/语义层先行 → 问数试点 → 扩展 → 深水区写操作）与快手容错率判断（治理容错高、问数容错低），不另行重排优先级。

## 痛点与风险

口径黑盒（生成的 SQL 没人看得懂→信任崩塌）、语义层建设滞后（最大瓶颈）、Token 成本、幻觉（写操作必须人工审批）。
结束语：Data Agent 终局不是替代数据团队，而是**把数据团队从"取数机器"升级为"语义资产运营者"**。

## 技能要求（报告 5.3 五角色）

| 角色 | 技能 |
|------|------|
| 数据工程师 | SQL/数仓建模 + Python + MCP 工具开发 |
| 算法工程师 | 语义层/指标、RAG、评测（离线评测集+线上监控） |
| 平台工程师 | Agent 编排（LangGraph 等）、多租户、成本治理 |
| 业务分析师 | 口径定义、本体建模、QA 对运营 |
| 安全/合规 | 行列级权限、审计、数据分级 |

## 与已有积累的对照

- 两段式 NL→MQL→SQL ↔ **DataAgent搭建骨架与六范式** 的 ChatBI 五级保障（同思路：LLM 不直连库、确定性隔离）
- 语义层 ↔ 指标卡片库/监管口径文档——监管行业手里就有现成的"语义资产"
- Vanna QA 对资产 ↔ 掌柜问数 RAG 的问答对回流；快手先治理后问数 ↔ 数据智能学习模块已有的快手实践解读

DSH（Data Super Hero）、SEGA 评测分、Berdite 等名词未能独立交叉验证，以报告原文为准；Databricks/Snowflake/Vanna/WrenAI/DB-GPT/快手路线等为可验证的公开事实。
