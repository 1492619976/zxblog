# 货拉拉 DataAgent 策略复盘 Workflow 解读

厂商实践：HClaw（货拉拉内部基于 Claude Agent SDK 的企业级 Agent 平台）把 DID 因果复盘 SOP 跑成 Dynamic Workflows 多 Agent 工作流。

## 一、业务场景与 SOP

货运供需时空波动 → 运营动态调策略 → 上线后需科学验证效果（指标前后变化会被季节性/市场趋势/同期活动干扰）→ 用 **DID 双重差分**估计增量效果。

人工沉淀**七步 SOP**：方案设计（定处理组/对照组/时间窗/DID类型）→ 数据获取 → 数据校验（样本/日期/字段/完整性）→ 效果估算（DID回归出 ATT/显著性/95%CI）→ 稳健性检验（平行趋势/安慰剂，不过则换对照组重跑）→ 归因分析（城市/指标/业务维度下钻）→ 报告输出。

示例报告数字：ATT +12.34% [8.21%, 16.47%]，p<0.001；归因瀑布=策略直接作用 50.3% + 渠道触达 23.1% + 用户结构 7.5% + 季节 4.8%（稳健性表中"更换对照组"一项 OCR 与视觉两版识别有出入 ±1pp，示例数字勿引用）。

痛点：多工具切换、周期长、重复多、依赖个人经验、难跨场景复用。

## 二、单 Agent 为什么失败

DID 复盘是典型 **Agent 长程任务**五特征：环节间明确依赖（校验完才能估算）、各环节需共享状态（口径/样本/时间窗/中间结果）、部分任务可并行（不同稳健性检验/异质性分析）、错误沿链累积放大、关键节点需判断与复核。挑战从"能否完成一次分析"变成"能否**稳定、可追溯**地完成长链条任务"。

## 三、四扩展机制对比（选型核心表）

| 维度 | Skills | SubAgents | Agent teams | Dynamic Workflows |
|---|---|---|---|---|
| 是什么 | Agent 遵循的提示词（工作规范） | 主 Agent 生成的独立工人 | 多 Agent 实例相互协作 | 可编排/扩展/运行 Agent 的 JS 脚本 |
| 谁决定下一步 | 主 Agent + 提示词逐轮思考 | 主 Agent 逐轮思考 | 主 Agent 逐轮思考（共享任务列表） | **Workflow 脚本代码** |
| 中间结果存哪 | 上下文窗口 | 上下文窗口 | 共享任务列表 | **代码内存变量** |
| 规模 | 每轮少量 | 每轮少量任务 | 几个长期对等体 | **数十到数百 Agent** |

选型结论：步骤相对固定、过程需追踪、结果需复核的长程任务 → Workflow。Skills 适合标准化单项任务；SubAgents 隔离上下文但主 Agent 要自行整合、口径易不一致；Teams 适合开放式协作但协作路径要额外管理。

## 四、三类踩坑（未引入 Workflow 前）

- **A 目标与规划类：Agent 自行缩小任务范围**。要求读候选城市数据做换对照检验，Agent 见数据量大自行判"没必要"跳过——不报错、流程继续，应被记录复核的判断变成了临场决定。根因：步骤和停止条件只存在于提示/上下文里。
- **B 记忆与经验类：关键约束在上下文传递中丢失**。前序明确要求稳健性检验+归因+保留 warnings，报告节点没完整带入 → 报告"不是错而是漏"。根因：长任务上下文持续增长，早期目标与约束被弱化。
- **C 执行与工具类：有返回结果 ≠ 执行正确**。方法选择节点定"合成对照"，估算节点却直接跑 DID；另一节点混淆 pre/post 期标签——每个节点都返回了结果，但不是同一套方法/样本/时间。根因：执行偏差+缺统一结果校验。

底层根因统一：**计划、中间状态、校验责任全靠主 Agent 在上下文里自维护**。解法不是加 Agent 数量，而是变成有明确依赖、能传状态、支持校验的显式结构。

## 五、最终方案：Workflow 承载 SOP

边界（"先固化方法，再划分节点"）：Workflow 是 JS 脚本但**只做编排+基础变量/判断/循环**，无文件系统/Shell 权限、不支持 import（含 import 的脚本运行前就失败），具体工作全放 Agent 节点。自然语言描述任务目标/步骤/输出要求即可生成初版，再按实际运行调节点边界。

伪代码四阶段：
1. `phase('方法选择+数据准备')` → `state.prep = await agent('选方法+最佳对照城取数')`
2. `phase('并行分析')` → `const [did,robust,attr] = await parallel([DID估算, 稳健性, 归因])`（三路互不依赖），`Object.assign(state,...)`
3. `phase('出报告')` → 把 state 中间结果 `JSON.stringify` 显式注入 prompt + 按 9 条规则输出（CI/evidence_level/归因区块/禁业务建议/追问结尾等）
4. `phase('对抗验证')` → **独立 Agent 逐条找茬**（验证者与执行者分离），`return state.check.ok ? state.report : fix(state)` 违规修复后重查

**坑→方案映射**（文章暗示、解读显式化）：A→步骤/停止条件进脚本代码，Agent 无权缩范围；B→中间结果走内存变量不靠上下文记忆；C→对抗验证节点+9条规则统一校验。

运行可观测：节点状态/执行耗时/当前进度单独查看。报告不只给"有效/无效"单一结论，数据缺失/检验未过/可信度不足会明确标注并给补充建议。
